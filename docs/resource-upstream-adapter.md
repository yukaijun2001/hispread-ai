# Resource integration adapter

Resource operations use the real JSON request/response contracts recovered from the frontend. The original private CCMAX server implementation and its administrator API were not supplied. A configured resource target therefore points to an adapter implementing these documented endpoints; this package does not claim compatibility with an unseen private protocol.

Only ADMIN can create or edit a saved `resource-target`. Configuration includes `baseUrl`, `apiKey`, `enabled`, optional `defaultTarget`, optional `upstreamPathPrefix` (default `/api`), `allowHttp` and `timeoutMs`. Multiple active targets require either explicit `targetId` or one unique default target. Supplier/operator requests cannot supply arbitrary destination URLs. Tokens are read from raw server storage by the gateway and are omitted by configuration GET projections.

HTTPS is the default. HTTP requires explicit administrator allowHttp. Redirects are never followed. DNS answers are checked for loopback, private, link-local, multicast and unspecified addresses. The `app.integrations.allow-private-targets` switch takes effect only in active `test` or `integration-test` profiles; it cannot enable private network access in production. Requests carry `Authorization: Bearer <apiKey>` and an `Idempotency-Key`; monitoring sources additionally support NONE or a validated custom HEADER credential. Timeout is capped at 120 seconds. Provider HTTP errors retain the HTTP status and use a stable code without echoing provider diagnostic bodies or credentials.

The adapter receives `/api/resources/supplier-submit`, `/api/resources/oauth/supplier-authorize`, `/api/resources/oauth/supplier-submit`, `/api/resources/oauth/supplier-session/{remoteId}`, resource `/submit`, `/dispatch`, `/oauth/authorize|complete|supplier-authorize|supplier-submit`, `/usage`, `/say-hi`, `/credential-refresh`, `/reauthorizations` and `/reauthorizations/{remoteId}`; job routes `/resource-lifecycle-jobs`, `/resource-proxy-replacements`, `/cc-intake/admin/priority/jobs`. Configured prefix replaces `/api` if needed. Input payload fields remain the recovered frontend fields, including requestKey, version, credentials, proxy selection, resource arrays and authorization codes. These are server-to-adapter payloads, not public response fields. The gateway adds `localResourceId` and resolves a selected same-tenant `proxyId` into its saved `input.proxyUrl` (or per-job-item `proxyUrl`) on the server so a remote adapter can actually use the configured authenticated proxy. Proxy credentials are not part of browser projections.

Responses are JSON objects. Submission/dispatch require explicit `state` (`SUCCESS`, `PENDING`, `UNKNOWN`, `FAILED`); success may include `laneId`, `resource`, `resourceData`, or usage. OAuth authorize can return `sessionId`, `authUrl`, `expiresAt`; the server emits a local opaque session id and stores the remote mapping. Usage can return `state: UPDATED`, `amount`, `currency`, `queriedAt`. Refresh/reauthorization preserve `status`; jobs return their actual `state`, remote id and item results. A request timeout or 5xx persists UNKNOWN rather than retrying a potentially completed submission. Replaying a local request key never issues another create. Changed request content returns 409. Explicit reconciliation queries the existing remote operation; it never blindly resubmits a create.

Operation state and credential material are durable PostgreSQL entities. Credentials remain in server JSONB and are projected out of list/detail/job responses. Supplier/member/operator scope is rechecked against each referenced resource/project, including after a project grant is revoked. This package currently does not add database-level field encryption; protect the PostgreSQL volume and encryption key boundary in a real deployment.

## Maintenance operation lookup and reconciliation

The console provides GET `/api/resources/{resourceId}/operations/{operationId}` and POST `/api/resources/{resourceId}/operations/{operationId}/reconcile`. Bearer clients use the same suffix under `/api/open/v1/ccmax/resources`. The path resource must match the original local operation, belong to the caller's visible scope, and use type USAGE or CREDENTIAL-REFRESH. GET requires resource read access; POST also requires resource write/dispatch access through the operation service. Bearer requests use the existing account API key and do not require a console session or CSRF token. These are local endpoints; CUSTOM reconciliation continues to read its original configured adapter operation route.

The response preserves the operation result plus `operationId` and `resourceId`. Inspect `state` rather than treating HTTP 200 as success. Native credential refresh returns UPDATED only after its refresh response and readback are confirmed. If that response is lost, UNKNOWN survives backend restart; keep the original request key and query/reconcile it. A new key is rejected while an earlier native refresh is unresolved. Native read-only reconciliation can confirm account readability but cannot reconstruct the missing refresh receipt, so it retains UNKNOWN and never resends refresh. Server-only binding snapshots and credentials are omitted from responses. See `ccmax-native-integration.md` for the process-fault evidence and remaining live acceptance boundary.

Native OAuth completion similarly commits its completion operation and submitted session before contacting the provider. Keep the original callback/request key; exact replay returns its saved result. Query first-intake through its original session/submission ID and reauthorization through the original resource/authorization ID or `/reauthorizations/current`. A lost exchange receipt remains UNKNOWN; do not generate another authorization or resubmit the callback under a new key. Session/target concurrency locks and submitted-state checks prevent another exchange after backend restart. These guarantees cover native exchange, not CUSTOM durability or authorization-link generation. Internal native-session/claim/mapping fields are never public response data.

Without an enabled configured target, upstream actions return HTTP 503 with `RESOURCE_UPSTREAM_NOT_CONFIGURED`, and no local delivered-success record is fabricated. Local drafts, NewAPI material recognition/preview/storage, project assignment, filtered summaries and operation history remain available. Proxy testing now verifies HTTP CONNECT / HTTPS proxy / SOCKS5 authentication and a bounded HTTPS egress IP request; see `docs/resource-integration-implementation.md` for protocol selection, actual New API compatibility, and validation details.

Verification: `ResourceIntegrationTest` uses Java's local fixture HttpServer under the test-only private-target allowance. It checks a successful real HTTP request, bearer key/path, persistent delivery, replay without a second call, changed-payload conflict, real provider 422 failure with redacted diagnostics, no-target 503 without creating a resource, SSRF fail-closed policy, proxy protocol rejection of a plain HTTP service, OAuth remote/local id mapping, lifecycle progress and replay, usage update and failure preserving an already successful delivery, and cross-tenant denial before network access.


`protocol: CUSTOM` selects this adapter contract. `protocol: NEWAPI` selects the published New API administrator channel protocol for mapped existing channels; it does not implement CCMAX private OAuth/intake. See [resource integration implementation](resource-integration-implementation.md).
