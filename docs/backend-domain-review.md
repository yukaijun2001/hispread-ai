# Backend domain review

Reviewed 2026-11-09 (Asia/Shanghai). Scope: `BusinessSupport`, `QuotesController`, `ResourcesController`, `TeamController`, `FinanceController`, `PlatformFinanceController`, their Store/Auth contracts and the corresponding recovered frontend requests. This is a bounded source review with PostgreSQL integration evidence, not a production audit or proof that all upstream integrations exist.

## Verified local flows

- Cookie session, tenant ownership and permissions are enforced server-side. ADMIN alone uses a global scope. Supplier writes derive their tenant from the session; ADMIN creation must specify an existing supplier. Ordinary member resource reads are limited to their own creator identity; department administrators can read their own department members. Member daily bills use the same creator/group boundary. Ordinary member department filters expose no other departments, and direct department-bill access returns 403.
- Quotes create in PENDING; only platform review grants APPROVED. Overlapping approved dates are rejected. Review and changes are recorded in audit entities. Price history supplies the currently effective value on quote list/detail and eligible-project reads, so scheduled reviewed prices take effect without a scheduler.
- NewAPI material can be recognized, previewed, durably saved and assigned a currently eligible quote project. Per-tenant request keys use a PostgreSQL advisory transaction lock. Save is explicitly local and does not assert external dispatch. List/detail/assignment responses exclude `material` and `originalRequest`; deliberate material access requires `resource.sensitive`, original-request access additionally requires `resource.request.read`.
- Team member creation inserts a real BCrypt-backed user and department membership. Members cannot grant their own projects; delegable projects and department transfers are checked server-side. Group administration updates the user's group-admin permissions.
- ADMIN manual/direct amounts → snapshot preview → statement creation → supplier confirmation → ADMIN offline proof record → supplier receipt is exercised against real PostgreSQL. Statement snapshots reject changes, payment amounts cannot exceed unreserved balance, and repeated request keys return the original durable record. Offline recording means an administrator records a transfer; it does not execute a transfer.
- CSV/XLSX exports contain a stored snapshot and real file bytes. XLSX is a valid minimal OOXML ZIP, not renamed CSV. Download and preview are owned by the user who created the export; files expire after seven days. SUMMARY/SUPPLIER grouping preserves currency and pricing basis.

## Findings fixed during this review

1. Assignment originally returned Store's complete intake object, including secret material. The response now removes both secret fields; a user without sensitive permission is covered by a targeted test.
2. Re-closing a FAILED payment originally subtracted its reservation twice. Only pending/approved records can now be closed; review, offline recording and close share the same per-payment transaction lock. The regression test keeps another payment's reservation unchanged after a repeated close.
3. Payment details originally omitted the recovered UI's `evidence.content`, `evidence.attachments` and `receivedAt` fields. These now have the expected shape, including all proof attachments and sanitized structural rich-text data.
4. Ordinary member bills originally depended on a main-account settlement permission; they now require resource access and creator scoping. Department access has a separate administrator check.

## Explicit boundaries and remaining limitations

- No real CCMAX, OAuth, external proxy probe or payment-provider configuration is supplied. Their execution/status methods return 503 with an explicit unconfigured-service message. No successful remote authorization, payment or resource creation is fabricated. Local jobs lists can therefore be empty.
- NewAPI keys and original materials are stored as plaintext in PostgreSQL JSONB. HTTP responses enforce permissions, but database/disk encryption and a managed secret-encryption key have not been added. This local persistence choice needs review before deployment with real credentials.
- NewAPI smart recognition supports the recovered JSON/channel shape and common key prefixes. Complex production provider heuristics and every upstream validation rule are not recovered; an ambiguous input asks for an explicit type. The system does not probe supplied endpoints.
- NewAPI assignment now requires an explicit `supportedIntakeTypes` match using the recovered 1/3/14/24/33/41/60 enum. `/projects/{id}/intake-channel-types` GET/PUT supplies the recovered numeric-array contract; unconfigured projects default to no compatible types. ADMIN eligibility/assignment derives the supplier from the intake row's database owner, ignoring a conflicting query tenant. Two suppliers can therefore approve the same project without mixing quote snapshots.
- Intake request-key replay compares a canonical SHA-256 fingerprint of tenant/name/normalized requests. The same payload remains idempotent regardless of JSON property order; a changed payload using the same key returns 409. Existing records without a stored fingerprint are compared using their saved original request order.
- Quote ranking has basic approved-quote data; complete capability sort/rank calculations and historical on-date price ranking are not implemented. Full arbitrary historical quote-version reconstruction is outside the read-time current-price helper.
- Statements and payments implement the local confirmation and recording flow, but no scheduler auto-confirms overdue statements. The endpoint rejects an expired manual confirmation rather than pretending that a deadline job ran. Batch generation is synchronous local work; there is no remote worker/queue.
- Manual input records are the available source of local platform daily accounting. No external ingestion or model-consumption collection is running. CCMAX monitoring/usage counts and supplier bills remain based on persisted records, not invented telemetry. Group-by daily reporting is implemented; large production datasets still need dedicated relational aggregation and indexes.
- The repository uses generic JSONB entities with application-level BigDecimal calculations and optimistic version checks. It is runnable and tested for this local replica; it is not a recovered copy of the original server's schemas or accounting ledger.

No independent live-origin mutation was made during this work. Remaining browser UI/role navigation validation is handled by the parent QA pass and should be read together with this bounded backend report.

## Professional five-role object boundaries

The earlier broad platform-business scope was superseded by `AccessPolicy`. OPERATOR business objects now require an enabled supplier whose database `ownerUserId` equals the authenticated operator. Supplier writes whitelist profile fields; injected owner, state, permissions, and secret properties cannot change governance. Operator-created suppliers are assigned to the caller, stay PENDING, and cannot add/login-bind users or self-assign ownership. Governance and project/configuration writes use the strict highest-administrator route. Quote review rejects the quote's creator/submitter even for ADMIN and requires approved supplier status. Formal quotation/submission eligibility requires an enabled APPROVED supplier.

Member project grants come only from the authoritative user profile; stale `agent.projects` snapshots never restore access after a revoke. Resource/intake/proxy access requires both current project grant and creator identity or a currently valid database department. Department administrators cannot create accounts, create/delete departments, move members, reset passwords, or delegate projects outside their own current set. Team creation uses the current role policy, not hardcoded sensitive grants; group changes invalidate affected sessions and group-admin scope is rechecked from the database.

Document routes distinguish qualification material from payment evidence. Operators can access qualification files only for assigned suppliers and cannot access payment proofs; finance can access payment proofs and not qualification material; members cannot upload company qualification/payment proofs or read another member's files. Proxy creation records creator/tenant, proxy access uses the same object policy, and replacement-option/update responses remove raw credential URLs. Raw NewAPI material is excluded from normal read/write responses and platform operators are explicitly denied material endpoints even if a broad permission is injected.

`ProfessionalDomainAuthorizationTest` adds three PostgreSQL HTTP negative-test scenarios spanning two operators, two suppliers and two members: scope and profile mass-assignment, self-review, resource/dept/project grant revocation, unauthorized team actions, raw material access, proxy access and real HTTP document downloads. The test fixture writes temporary local PDF bytes and removes them in `finally`. The parent coordinates the final full-suite result after this focused pass; no service restart was performed by this agent.

The final closure pass fixed public catalog projection and retained SDK records: submission reads now apply current object/project authorization and public redaction; reauthorization reads use the authorized resource owner and redact raw fields; replacement reads validate every resource and redact the result. Authorized members can now obtain project eligibility without being granted quote read access: the server evaluates the tenant's frozen quote internally, emits an opaque SHA-256 quote token and removes nested pricing data from member-facing project/resource/intake/SDK records. Assignment keeps the frozen pricing basis server-side. Revoking a member's project immediately empties eligibility and denies existing assigned intake/SDK submission reads. Direct department edits cannot orphan a member; transfers must be initiated through the destination department.
